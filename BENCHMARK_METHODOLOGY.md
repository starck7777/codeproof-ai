# Benchmark methodology

Each attempt uses a matching task version/environment and frozen per-attempt budgets. DirectPatch permits one public verification call. IterativeFix can repeatedly test/edit; PlanVerify requires a plan and public verification after the latest patch. Observable tool actions and brief operational summaries are logged, never hidden chain-of-thought.

Strict success means all trusted public, hidden and regression cases pass, only permitted source is exported, and no configured limit is exceeded. Timed out, cancelled or infrastructure-failed attempts cannot be strict successes. Infrastructure failures are counted separately and excluded from the valid evaluated denominator. Report counts always show sample size. Cost per success is total valid evaluated cost / successful evaluated attempts; undefined if there are no successes or cost data is missing. Median and nearest-rank p95 duration use valid evaluated attempts. Missing usage is null, distinct from zero. Cached tokens remain in raw usage records when supplied; special cached pricing is not implemented.

Demo results are deterministic workflow examples, not model quality measurements. DirectPatch and PlanVerify read an evaluator-side reference to create scripted source changes; the real grading phase still runs in Docker. IterativeFix intentionally retains the starter to show failure. Tight tool budgets produce an unevaluated timeout. No synthetic latency, token or price metrics are presented as measurements. Demo and live exports retain explicit labels; normal comparisons separate modes.

All 12 tasks have one public case, two hidden cases and one regression case in `cases.json` (fresh-bucket tests repeated calls to expose shared state). Pytest files provide readable fixture documentation; the isolated trusted runner uses the JSON cases as the authoritative suite. Starter and reference validation must run in Docker, not on the host. Requirements describe behavior assessed by hidden cases.

Public source includes hidden fixtures and references: humans and pretraining corpora can see them. This is separation from the repair environment, not contamination resistance. Four cases per task are a deliberately small hackathon suite, not comprehensive software verification. Report repeated-run variability as repetitions; no pass@k estimator or blended score is used. Compare only matching task selections/versions, strategy or model axes, budgets and environments. Current comparison UI exposes rates, durations, costs, a per-task matrix, sample sizes and configuration-difference warnings. Automatic compatibility grouping is a follow-up.
